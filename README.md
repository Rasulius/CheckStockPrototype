# CheckStock

Веб-прототип учёта остатков на складах фулфилмента. Показывает, где физически находится товар (по складам/ФФ), сколько доступно, сколько зарезервировано под FBS, а также движения: приход, перемещение между ФФ, резерв/отгрузка FBS, отправка и приёмка FBO, транзит и история операций.

Стек: **Python 3.12, FastAPI, SQLAlchemy 2.0 (sync), Alembic, Jinja2, Pydantic v2**. БД: **PostgreSQL 16** (основной режим) или **SQLite** (через `DATABASE_URL`, тестовый/облачный режим).

## Запуск

Требования: Docker + Docker Compose. (Для локального запуска без Docker — Python 3.12 и зависимости из `pyproject.toml`.)

### Windows (PowerShell)
```powershell
# PostgreSQL (по умолчанию)
.\run.ps1

# SQLite (без контейнера PostgreSQL)
.\run.ps1 -Sqlite

# Остановка / логи
.\run.ps1 -Down
.\run.ps1 -Logs
```

### Linux / macOS (bash)
```bash
chmod +x run.sh

# PostgreSQL (по умолчанию)
./run.sh

# SQLite (без контейнера PostgreSQL)
./run.sh --sqlite

# Остановка / логи
./run.sh --down
./run.sh --logs
```

После запуска приложение доступно на **http://localhost:8000**.

- PostgreSQL-режим: поднимаются сервисы `db` (postgres:16-alpine) и `app` (`docker-compose.yml`).
- SQLite-режим: поднимается только `app`, БД хранится в volume `sqlite_data` (`docker-compose.sqlite.yml`), контейнер PostgreSQL не требуется.

Переключение БД также задаётся переменной окружения `DATABASE_URL` (`.env` / `.env.example`), без изменений в интерфейсе:
- PostgreSQL: `postgresql+psycopg://...`
- SQLite: `sqlite:///./data/checkstock.db` (или другой путь)

## Проверки

### Автоматические тесты
Локально (при установленном окружении):
```bash
python -m pytest -q
python -m ruff check .
python -m ruff format --check .
```
В Docker (PostgreSQL):
```bash
docker compose run --rm --entrypoint /bin/sh app -c "pip install -q '.[dev]' && pytest -q"
```
Тесты выполняются на реальной БД, в конце проверяется согласованность (`assert_consistent`).

### Какие сценарии тестировались
- **Начальные данные/seed**: идемпотентный seed (2 ФФ, 3 артикула, 5 приходов), повторный запуск не дублирует операции.
- **Приход**: увеличение остатков, запись в журнал, идемпотентность по ключу.
- **Перемещение между ФФ**: списание с источника, транзит, приёмка на целевой ФФ, идемпотентность приёмки.
- **FBS**: резервирование (on_hand/reserved/available), отправка клиенту, отмена резерва, идемпотентность отправки.
- **FBO**: отправка на склад МП (списание/транзит), приёмка, идемпотентность.
- **Нехватка/валидация**: запрет операций сверх доступного на ФФ (`WAREHOUSE_SHORTAGE`), запрет при суммарной нехватке (`TOTAL_SHORTAGE`), запрет операций на архивный ФФ, недопустимые переходы статусов.
- **Склады (ФФ)**: создание/переименование/уникальность активного имени, soft delete (архивация) с сохранением остатков и истории.
- **UI/экраны**: рендер основных страниц (остатки, операции, FBS/FBO, склады, история, карточка товара), формы/предзаполнение, ограничения ввода по доступному остатку, подсказка «Остаток: N шт.».
- **Согласованность**: `reserved <= on_hand`, неотрицательные остатки, соответствие документов/балансов/журнала; smoke-проверка запуска в **SQLite**-режиме (`/health`, основные страницы, выполнение операции).

## Ключевые решения (как это работает)

- **Модель состояний товара**: каждая единица учитывается в одном из состояний — свободно на ФФ, в резерве FBS, в транзите перемещения, в транзите FBS, в транзите FBO, принято на складе МП. Остатки «в пути» выводятся по открытым документам (`transfer` в `in_transit`, `shipment` в `shipped`).
- **Баланс + журнал в одной транзакции**: `stock_balances` обеспечивает быстрый просмотр остатков, `stock_movements` — аудит/историю. Любая изменяющая операция атомарно обновляет баланс, создаёт проводки и документ. В PostgreSQL журнал защищён от изменений (append-only).
- **Сервисный слой и целостность**: бизнес-логика изменения остатков сосредоточена в `app/services/`; маршруты (HTML/JSON) тонкие. Перед списанием/резервом строки баланса блокируются в детерминированном порядке `(product_id, warehouse_id)` (в PostgreSQL — `FOR UPDATE`), проверки выполняются в транзакции; `CHECK`-ограничения БД — дополнительная защита инвариантов.
- **Идемпотентность**: создание операций принимает `idempotency_key` (уникальность документа), повторные вызовы не создают дубликаты; переходы статусов (`ship/receive/accept/cancel`) безопасны при повторе.
- **Нехватка без частичного списания**: если на выбранном ФФ недостаточно, операция отклоняется (`WAREHOUSE_SHORTAGE`) с альтернативами; при общей нехватке — `TOTAL_SHORTAGE`.
- **Склады (ФФ)**: удаление в UI/логике — soft delete (архивация, `is_archived/archived_at`) с сохранением остатков и истории; операции на архивный склад запрещены (кроме допустимых завершений по уже созданным документам).

## Структура (основное)
- `app/` — приложение FastAPI (маршруты, сервисы, модели, шаблоны, статика)
- `migrations/` — миграции Alembic (PostgreSQL)
- `tests/` — автоматические тесты
- `seed.py` — идемпотентные тестовые данные
- `docker-compose.yml`, `docker-compose.sqlite.yml` — запуск с PostgreSQL / SQLite
- `run.ps1`, `run.sh` — скрипты запуска
